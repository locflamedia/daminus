# System architecture

Daminus is an on-demand health check for small fleets of servers: you open the app, press Scan, read the results, and close it. Nothing runs in the background and nothing is installed on the servers.

## Shape

One core crate plus a thin Tauri shell and a Vue front end (a modular monolith).

```
┌──────────────────────── macOS app ────────────────────────┐
│  src (Vue 3 + TS)                                          │
│    api/        the only code that imports @tauri-apps/*    │
│    stores/ features/* ui/ layout/ i18n tokens              │
│                     ▲  typed IPC (commands + one event     │
│                     │  per domain, e.g. scan://event)      │
│  src-tauri (thin shell)                                    │
│    commands · events · scan run state · keychain · tray    │
│    GUI env · logging · capabilities / CSP                  │
│                     ▲  plain Rust calls                    │
│  crates/core (daminus_core, no Tauri)                      │
│    domain (pure) · contracts · checks (scripts, manifest)  │
│    ssh transport · url probe · scan service + evaluate     │
│    discover · ai · store (FsStore) · redact                │
│    bin/daminus-dev (feature `cli`)                         │
└─────────────┬──────────────────────────────┬──────────────┘
              │ system `ssh` (user's config,  │ HTTPS from the Mac
              │ agent, ProxyJump)             │
              ▼                               ▼
     servers: one read-only           project URLs (status,
     bundle per host, NDJSON out      latency, TLS, domain)
```

### Boundaries

- **`crates/core`** is pure Rust and knows nothing about Tauri. `domain/` must not import `ssh`, `probe`, `ai` or `store`, including aliased and grouped imports (`scripts/check-core-boundaries.sh` in CI, with a fixture test).
- **`src-tauri`** wires core into commands, events, the tray and the keychain. It holds no business rules.
- **`src/api/`** is the only front-end code allowed to import `@tauri-apps/*` (ESLint bans static and dynamic imports and the `__TAURI__` / `__TAURI_INTERNALS__` globals elsewhere). Everything else goes through its typed wrappers.
- **Bindings:** Rust types are exported to TypeScript with `ts-rs` into `src/api/bindings/`, committed, and checked for drift in CI.

### Check runtime

`crates/core/checks/` holds `manifest.json` (every check: group, where it runs, script, allowed commands, fact meaning and severity rule), `prelude.sh` and one script per remote check. They are embedded with `include_str!`. `checks::bundle::build` concatenates the prelude, a block of single-quoted variables (limits from Settings › Scan, and the host's components from `projects.json`: `DAMINUS_PATHS`, `DAMINUS_COMPOSE`, `DAMINUS_PM2`, `DAMINUS_DB`), one subshell function per enabled check, and `main`, called with stdin from `/dev/null` on the one-line tail: the shell has read the whole bundle before any check runs, and a check that reads stdin gets EOF instead of the rest of the bundle. When the caller sets `DAMINUS_HANGUP=1` (the SSH transport does, and keeps stdin open), the tail also starts a watcher that reads stdin: end of file means the client went away (Ctrl-C, app quit, lost connection) and the bundle stops its own process group, instead of running on until the server-side `timeout`. The tail ends with `exit 0`, so the shell never waits for more input. `checks::ndjson::Parser` reads the output incrementally (see ADR 0002). The UI imports the same manifest through the `@checks` Vite alias; labels are `checks.<id>.name|desc` in `src/i18n/`.

In CI (job `shell`), `scripts/check-harness/run.sh` runs the bundle in `ubuntu:24.04` and `debian:12` containers with a read-only root, as a normal user, with only `/tmp` writable, no network and no capabilities. `docker`, `pm2`, `dmesg`, `mysql` and `psql` are shims on `PATH` that print recorded output (`docker inspect` without a `--format`, or one reading `Env`, prints the canary environment; `mysql` and `psql` refuse, like a server, any login that is not the one in the harness `.env` files, and `docker exec` fails on an `-e` that carries a value). The project folder holds 50,000 files and the whole bundle must finish in under 60 s; `~/.pm2` and `storage/logs` are small tmpfs mounts that look like a running pm2 daemon's home and hold a sparse 600 MiB log. It fails if any line is not NDJSON v1, if a `CANARY_*` value (process env, project `.env`, shim output) reaches stdout, or if `$HOME` or `/tmp` hash differently afterwards. Each check's output is kept as golden NDJSON in `fixtures/ndjson/<distro>/`, shared by the parser tests and the fake transport, and compared by shape on every run. The setup scripts (login test and discover, below) run in the planted container the same way, and their records are kept in `fixtures/discover/<distro>/`.

**Database credentials (`db.size`).** The script reads the component's `.env` on the server as text, never with `source`, `.` or `eval`: a hand-written `KEY=VALUE` reader (`sed` and `case`) that understands `export`, CRLF, comments, and double, single or no quotes (inside double quotes `\\` and `\"` are decoded; any other backslash, `${` or an unclosed quote there, or an unclosed single quote, is `Unknown(unsupported)`, because most dotenv readers decode or expand those and the text is then not the password; a multi-line value is the same; the last assignment wins). The login comes from the first of `DB_USERNAME`/`DB_USER` with `DB_PASSWORD`/`DB_HOST`/`DB_PORT`, a simple `DATABASE_URL` (`scheme://user[:password]@host[:port]/db`, no query, no percent-encoding), or `MYSQL_*`/`POSTGRES_*` (a password alone stands for the image's default user: root with `MYSQL_ROOT_PASSWORD`, `postgres` with `POSTGRES_PASSWORD`). The password reaches the client without touching argv or disk: for MySQL `printf` (a builtin) pipes an option file to `mysql --defaults-extra-file=/dev/stdin`, also through `docker exec -i`; for Postgres `PGUSER`, `PGPASSWORD` (and `PGHOST`/`PGPORT` on the host) are exported and `docker exec -e NAME` names them without values. Inside a container the client talks to its own server, so host and port are ignored, even when the `.env` points at another host. SQL is one constant `SELECT` per engine (`Q_MYSQL`, `Q_PG`, a total row and the five largest tables), and the database name reaches it through the connection (`DATABASE()`, `current_database()`), never string concatenation. `crates/core/tests/check_scripts.rs` enforces this: SQL only in single-quoted `Q_*` constants that start with `SELECT`/`SHOW`, one statement, no write or lock keywords, only a short list of functions, and every `mysql`/`psql`/`docker exec` call limited to a fixed option set with `-e "$Q_…"`; no fact, `emit` or `echo` may mention a login variable. The group has one 40 s allowance: the docker daemon is asked once for all container databases, and every call (daemon, `docker inspect`, client) runs for at most what is left of it, so a hung daemon cannot take more than the allowance from the host's budget. The outcome follows the client's exit code only (0 result, 124 timeout, 126/127 missing, anything else `needs_perm`) and no stderr text is read, so no user, host or error message can reach a fact.

`scripts/check-harness/db-real.sh` (also in job `shell`) starts MySQL 8 and Postgres 16 containers and runs the `db.size` bundle against them twice over: in read-only containers with the real clients (Ubuntu's MySQL client and Debian's MariaDB client) and through `docker exec` on the runner. Every `.env` holds canary logins that are the servers' real passwords, one full of quote, backslash, `#`, space, `$HOME` and backtick, in single quotes and in double quotes with `\\` and `\"` escaped. It fails if a canary reaches stdout, the recorded argument list of any client or docker call, or what `ps` showed during the run; if `$HOME` and `/tmp` (or the home and temp folders given to the host shell) hash differently afterwards; or if a logical dump of both databases and the servers' write counters differ before and after all runs. Wrong password, unreachable server and unknown database must read `needs_perm`; an unknown container, `missing`.

**Security checks (`sec.*`).** All read-only, none opens a file's content except to hash its first MiB, and none reads a process's command line or environment (they can hold passwords).

- A finding is one fact with the evidence as `target`, no `value` (so a zero-byte PHP file cannot read as "looked, found none") and an evidence fingerprint `fp`; a check that looked and found nothing prints one fact with value 0 (`sec.upload_php` and `sec.recent_change` one per project folder, the others one with an empty target). File findings (`sec.upload_php`, `sec.tmp_exec`, `sec.preload`) are fingerprinted `size:mtime:sha12`, where `sha12` is the first 12 hex digits of the SHA-256 of the file's first MiB; `sec.ports` is `port/process name`; `sec.miner` is `name|executable path`; `sec.recent_change` is the SHA-256 of the sorted file names. The 50 newest findings of a check are listed, each with the total in `data.total`.
- `sec.miner` walks `/proc`: the name is `/proc/PID/comm`, the executable is the `exe` link read with `find -printf %l`, and kernel threads (`PF_KTHREAD` in `/proc/PID/stat`) and zombies are left out. It reports a known miner name (of the process or of the file it runs from, since a miner can rename its process), or an executable that was deleted from `/tmp`, `/var/tmp`, `/dev/shm`, `/run`, `/dev` or memory (`memfd:`). A deleted binary anywhere else is what a package upgrade leaves behind, so it is not reported. Coverage is `seen/total`: with fewer than all seen (another user's `exe` is unreadable without root) a run with no finding is `Unknown(needs_perm)` with `data{seen, total}`, never ok. A process that ended while the executables were read leaves the total instead of counting as unseen.
- `sec.ports` reads `/proc/net/tcp` and `tcp6` (no `ss` needed, and a minimal image has none) for LISTEN sockets bound to `0.0.0.0` or `::` on 3306, 5432, 6379, 27017 and 2375, and finds the holder through the socket links under `/proc/PID/fd` (the SSH user's own processes only).
- Checks that need GNU `find` (`-printf`, `-lname`, `-perm /MODE`) run `find_ok` first and answer `unsupported` on busybox or BSD instead of calling an unread folder clean.
- The scripts read `DAMINUS_PROC`, `DAMINUS_TMP_DIRS` and `DAMINUS_PRELOAD_FILE` so tests can point them at a fake `/proc`, temp folders and a preload file; the app never sets them.
- The harness (`run.sh`) runs every check twice: in a clean container, whose output is the golden `fixtures/ndjson/<distro>/sec_*.ndjson` (a healthy host, which other tests replay), and in a container made to look compromised (`probe.sh` with `PLANT=1`: a miner and a deleted hidden job running from `/tmp` with a canary on the miner's command line, listeners (6379 and 8080 held by perl on every address, 3306 on every address by a process named `mariadbd`, 5432 on 127.0.0.1 only, so `sec.ports` must report 3306 and 6379 and neither of the others), executables in `/tmp` and `/dev/shm`, a PHP file in `uploads`, and `/etc/ld.so.preload` bind-mounted), whose output is `fixtures/ndjson/<distro>/infected/` and is asserted with `jq`: the findings, their fingerprints, and no leak of any canary.

**URL probes (`url.*`, host `@local`).** `UrlProbe::probe(url, ProbeChecks)` runs, side by side and per Settings › Scan group, `url.http` (and `url.tls` for `https` URLs) when `uptime` is on and `url.exposed` when `security` is on; with both off no URL is probed. The Mac is covered for a group (so a result that disappears is "fixed") when its probes ran: `uptime` and/or `security`.

- `url.tls` has its own TLS client (`tokio-rustls`) whose verifier only records. It asks the platform verifier (`rustls-platform-verifier`, the macOS trust store) about the chain, keeps the verdict and the end-entity certificate, and accepts the handshake whatever the verdict; signature checks still go to the real verifier. `notAfter` is read from the certificate (a short DER reader in `probe/cert.rs`), so it is known for expired, self-signed and wrong-name certificates. The macOS verifier reports an expired chain that is also untrusted as a generic error, so `untrusted` can read false there; the outcome is still crit through `expired`. Fact: `value` days left (negative when expired), `data{not_after, expired, untrusted, mismatch}`; the manifest rule is `days_left` 14 / 3 with those three flags forcing crit. A verifier names one problem and checks dates first, so for an out-of-date certificate it is asked again for a day inside the validity period: `untrusted` is about the chain and `mismatch` about the name (checked with `rustls-webpki`), never about the date. A failure before a certificate arrives is an unknown fact with `data.error`.
- `url.exposed` asks for `/.env` and `/.git/HEAD` at the root of the site with its own client: redirects are followed only on the same host (at most 5) and a redirect that was not followed means the file was never read, so a run that found nothing and met one is `unknown: unsupported` with `data.error` = `redirect_other_host` or `redirects`, never clean (a finding in the other file stands), only a `200` counts, and at most 4 KiB of the body is read and judged in memory (an `.env` has `KEY=VALUE` lines, with names of letters, digits, `_` and `.`, a possible BOM and spaces around `=`, and is not HTML; a `HEAD` is `ref: refs/…` or a commit hash). The fact is `target` = the configured URL, `value` = files exposed, and `data` holds only `{exposed, matched_keys}` (`/.env:DB_PASSWORD`: key names, never values). Both clients use no proxy, connect 5 s, whole request 10 s.
- `url_warning(url)` is the setup warning for a URL only this Mac can reach: `Loopback` (`localhost`, 127/8, `::1`), `PrivateNetwork` (10/8, 172.16/12, 192.168/16, 100.64/10, `fc00::/7`, `.local` / `.internal` / `.lan` names, single-word hosts) or `LinkLocal` (169.254/16, `fe80::/10`). It judges the text only, since setup must not wait for DNS.

### Scan flow

`scan_start` (single flight) → `ScanService` → in parallel { `Transport.run(bundle)` per host, `UrlProbe` } → NDJSON lines (size-limited, control characters filtered) → `CheckFact` → event `scan://event` (with `scan_id`, `seq`) → on completion, save a raw snapshot (discarded if the scan was cancelled) → UI and tray call `evaluate`.

**Transport.** `ssh::SshTransport` spawns the system `ssh` with one argv entry per argument (no local shell): `ssh -T [-F cfg] -o BatchMode=yes -o StrictHostKeyChecking=yes -o UpdateHostKeys=no -o ForwardAgent=no -o ForwardX11=no -o ClearAllForwardings=yes -o PermitLocalCommand=no -o RemoteCommand=none -o LogLevel=VERBOSE -o ConnectTimeout=<5|10|30> -- <alias> "sh -c 'if command -v timeout …; then exec timeout -k 5 90 sh -s; else exec sh -s; fi'"`, the bundle on stdin. Each run is its own process group, killed when the run ends, is dropped (cancel, budget) or on `shutdown` (app quit, Ctrl-C). `StrictHostKeyChecking=yes` and `UpdateHostKeys=no` override the user's config (`-o` wins over the file), so an unknown host is always reported and `known_hosts` is never written, not even by ssh's own key rotation. Stderr (which also carries the server's pre-auth banner) is read as raw bytes, split into lines of at most 1 KiB (the rest of a longer line is skipped), decoded lossily and fed to a classifier (auth, host key unknown/changed, DNS, refused, no route, timeout); only the last 4 KiB is held, in memory, and it never reaches a snapshot, event, log or the AI. For an unknown or changed host key, a second `ssh` through the same config (ProxyJump applies) with an empty temporary `UserKnownHostsFile`, `StrictHostKeyChecking=accept-new` (extra options come before the forced ones on the command line, and ssh keeps the first value) and `PreferredAuthentications=none` records the offered key without offering any user key; `ssh-keygen -lf` reads its fingerprint and the file is deleted. The real `known_hosts` is never written. `LogLevel=VERBOSE` prints `Authenticating to`/`Authenticated to` per hop: two seconds between them without output is reported as an SSH agent waiting for approval (`agent_wait`).

**Budget.** Each host has 90 s from its first byte of output (fixed, also enforced by `timeout` on the server when present). Before any output (connect, jump hosts, agent approval) it has as long again. `ConnectTimeout` covers only the TCP connect and handshake. Hosts run at once up to Settings › Scan `hosts_at_once` (Auto = number of hosts, at most 8); URL probes run alongside.

**Outcome of a host.** `end` line → Reached. Otherwise: budget spent or remote exit 124/137 → Timeout (lines already received are kept; groups whose `step` line arrived before the timeout count as covered, later groups do not); a classified ssh failure before `begin` → AuthFailed / HostKeyUnknown{fp} / HostKeyChanged{fp} / Unreachable{cause}; anything else → Partial. If every host failed with DNS/no route, every URL failed the same way and at least two targets failed in total, the scan ends with `LocalNetworkDown` and nothing is saved. A lone failing target (one host with a mistyped `HostName`, a VPN that is down) is saved with its own outcome.

**Events.** `ScanEvent{scan_id, seq, kind…}`: `host_started`, `agent_wait`, `host_running` (the bundle's `begin` arrived), `step{group, ms}`, `fact`, `host_finished{outcome, ms, facts, dropped}`, then one of `done{snapshot_seq}`, `cancelled`, `failed{error}`. `seq` rises by one per event. `ScanService::status()` returns the live `ScanRun{scan_id, started_at, next_seq, hosts}` (`next_seq`: every event below it is already folded in, so a webview that hydrates mid-scan skips those and re-reads the status on a gap); a second `start` while one runs returns the running `scan_id` (`joined`). The event receiver must be drained continuously; once a scan is cancelled, an event that cannot be queued is dropped rather than waited on, so a stuck listener never blocks cancel.

Snapshots store raw facts only. Delta, expected, stale, rollup and severity are computed at read time by one pure function, `evaluate(history, config, manifest, now)`, shared by the CLI, commands, menu bar and AI payload. Severity thresholds live in the check manifest (plus user settings), so changing a threshold takes effect without rescanning.

### Setup flow

Setup turns `~/.ssh/config` into suggested projects. It is core and service only (`crates/core`); the screens come later. It reuses the scan's `Transport`, so the user's own ssh config, ProxyJump, SSH agent and host key policy apply, and nothing runs on a server except read-only scripts.

1. **Host list** (`ssh::config`). A light read of the config text, following `Include` (relative to `~/.ssh`, `~`, `*` and `?` in any path component, 16 levels, a file that is already being read is not read again, nothing is written), lists the `Host` aliases and says why each entry left out was: `wildcard` (`*`, `?`, `!`), `match` (a `Match` block), `no_host_name` (no `HostName` in its own block, in a `Host` pattern that applies, or before the first `Host` line, which ssh applies to every host) or `invalid_alias`. Each left-out entry is listed once. The home folder is `$HOME`, else the user database's, and a `-F` file is read even with neither. A missing file, or a file with no usable host, is the empty state (`empty: no_config | no_usable_hosts`); reading again after the user edits the file is just listing again. What a connection really uses (HostName, User, Port, IdentityFile, ProxyJump, known-hosts files, HostKeyAlias) is never worked out here: `ssh -G -- <alias>` computes it with ssh's own rules (`ResolvedHost`).
2. **Host key** (`ssh::hostkey`). `ssh-keygen -F <name> -f <file>` (hashed names included) looks the host up in each known-hosts file ssh would read (`[host]:port` off port 22, `HostKeyAlias` first), `ssh-keyscan -T 5 -t ed25519,ecdsa,rsa` reads the keys the host offers, and `ssh-keygen -lf -` turns key lines into fingerprints; there is no known-hosts parser. A recorded key that the host does not offer is `changed`, nothing recorded is `unknown`. `ssh-keyscan` ignores ProxyJump and the user's config, so for a proxied host the offered key comes from the login attempt's own second `ssh` (see Transport). The app never writes `known_hosts`: an unknown host shows its fingerprint and the user accepts it once with `ssh <alias>` in Terminal (screen 12's Retry is `SetupService::host_key`, which looks again without logging in). Every helper (`ssh -G`, `ssh-keygen`, `ssh-keyscan`) runs in its own process group with a time limit; the group is killed when the limit passes or the caller stops waiting (a cancel), never after the program exited and was reaped, when the group id may already be another's.
3. **Login test** (`discover/login.sh`, `SetupService::start(Step::Test, …)`). A small bundle through `Transport`: `uname`, `/etc/os-release`, `id` (user, uid, and only the `docker`, `adm` and `systemd-journal` groups), whether the docker daemon answers (`docker_ok`: ok, no permission, stopped, missing), GNU `find`, and for each project folder asked about `readable`, `denied` or `missing`. While authentication waits (1Password, Secretive) the run emits `agent_wait`.
4. **Discover** (`discover/discover.sh`, `Step::Discover`). Records, one JSON line each, between `begin` and `end`: `vhost` (nginx `server` blocks from the first readable of `/etc/nginx/nginx.conf`, `/usr/local/nginx/conf/nginx.conf` and aaPanel's `/www/server/nginx/conf/nginx.conf`, and what it includes, read as text with an awk tokenizer: names, root, `proxy_pass` as `host:port` with an `upstream` resolved, TLS, `fastcgi_pass`), `compose` (from `docker ps -a --format` labels only: project, working folder, services, published ports; one-off containers left out), `db` (database images in containers, and `mysqld`/`mariadbd`/`postgres` processes by `/proc/PID/comm`), `pm2` (the pm2 rules above: `pm2_state` first, one `pm2 jlist` per `PM2_HOME`, only name, status, instances and `pm_cwd` read; another user's daemon is a `pm2_home` note), `port` (listening TCP ports with bind `any`/`loopback`/`other` and, for the SSH user's own processes, the process name and folder), `env` and `note` (docker without permission or stopped, no pm2 command, an unreadable `nginx.conf`). **A `.env` is never opened**: the file is only listed by `find -name '.env' -o -name '.env.*'` (example, sample, dist, template, tpl, bak and orig left out) under the usual code folders (`/var/www`, `/www/wwwroot`, `/srv`, `/opt`, `/home`, `/data`, `/app`) and the folders found above, and tested with `-r`. Names and paths come out through `json_str` or an awk check that drops a record with a quote, backslash or control character.
5. **Parsing** (`discover::RecordParser`). Same limits as the check parser (`LineBuffer`: 64 KiB lines, 8 MiB per host; `clean_line`); a `begin` with another bundle hash drops the run; records are accepted only between `begin` and `end`, each is checked (`SetupRecord::sanitize`: compose, pm2 and container names must satisfy `is_plain_name`, paths `is_abs_path`, hostnames a DNS charset, text is cut) and capped per kind. Lines that do not fit are counted in `dropped`, never repaired.
6. **Grouping** (`discover::grouping`, pure). Items are linked by evidence and each linked group becomes a project when it has a public domain or at least two parts; the rest is "Not in a project". Evidence: a shared registered domain (`shop-x.com`, `api.shop-x.com`; `www.` taken off, three labels under `co.uk`/`com.vn`), on any host; a shared folder on one host (web root, compose working folder, pm2 folder, the folder of the process holding the port a block proxies to: the same folder or one inside the other, after taking `public`, `dist`, `current`… off, never a shared folder such as `/var/www`, `/www/wwwroot`, `/srv` or a home); a `proxy_pass` to a local port that a compose project publishes. A `.env` joins the group whose folder is closest (above two groups' folders, as a monorepo's is, it joins none and is listed under "Not in a project"); a server block whose root is a shared folder (`/var/www/html`, `/`) is only a URL, and one that only proxies gets the folder of the process behind its port as its code folder; a database container joins its compose project; a database server that runs as a process (or a container with no compose project) is used when exactly one engine runs on a host where a project has a `.env`. A suggested database component has the engine, the `.env` path and the container but **no database name** (it is a value inside the `.env`, which discover never reads); `ProposedProject::to_project(database)` fills it in or leaves those components out. Ids are slugs of the domain's first label (else the compose project, pm2 app or folder name), made unique with `-2`, `-3`.
7. **`SetupService`.** `list_hosts`, `list_resolved`, `host_key`, `start(step, hosts, paths)` (single flight; a second call joins), `status`, `result`, `cancel`, `shutdown`, `validate`, `save`. A run is a scan-shaped job: hosts at once per Settings › Scan (`hosts_at_once`, Auto = number of hosts, at most 8), `connect_timeout_s`, a budget from the first byte (30 s for the login test, 90 s for discover; as long again before any output), events `host_started`, `agent_wait`, `host_running`, `item{SetupRecord}`, `host_key{HostKeyInfo}`, `host_finished{outcome, ms, items, dropped}`, then `done`, `cancelled` or `failed` (a host task that dies ends the run with `failed`, so no listener waits for a `host_finished` that never comes; what the other hosts found stays). A cancel also stops a host key lookup in progress, and the budget counts from after `ssh -G`. Outcomes are the scan's `HostOutcome` (`AuthFailed` is `SshAuth`, an unknown key carries its fingerprint, a failure is per host and does not end the run). `result()` keeps, per host, the outcome, the `ssh -G` values, the host key info, the login result and the discovery, and the `Proposal` from every discovered host; a new run starts from the hosts it is given. `validate` returns `ProjectIssue{project, field, level, code}`: errors (empty, bad or taken id, empty name, a project with neither URL nor component, a URL that is not http(s)) stop `save`; warnings (`url_local_only{loopback|private_network|link_local}` from `probe::url_warning`, a repeated URL or component, a host that is not in the ssh config) do not. `save` upserts by project id (a project that replaces a saved one keeps its color and threshold overrides, and `validate` says so with the `replaces_existing` warning), keeps every other project, the "mark as expected" rules and the hosts' settings, lists the selected and used hosts in `hosts` (included), trims and dedupes URLs, and refuses a file written by a newer version.
8. **Dev CLI.** `daminus-dev [-F cfg] hosts` and `discover [--host A] [--database PROJECT=NAME] [--path P] [--dry-run]` run the flow from a terminal (progress on stderr, result on stdout; the projects are saved unless `--dry-run`); `setup-bundle login|discover` prints a bundle; `ndjson --records FILE` checks a records file.

`scripts/fake-server/e2e.sh` (job `shell`) proves the flow against a container with a real sshd (key login, an nginx config, docker/pm2/mysql shims, listeners, canary `.env` files): the host list with reasons, an unknown host key (the server's real fingerprint, the command to accept it, not stuck), a host reached through `ProxyJump`, a wrong key (`SshAuth`), a closed port, discover writing a `projects.json` that `daminus-dev scan` then scans, no canary anywhere (outputs, config folder, snapshots), `known_hosts` byte for byte unchanged (and no `~/.ssh` created), and the server's home and `/tmp` hashing the same afterwards. `crates/core/tests/setup_local.rs` runs `SetupService` over the real scripts through a local `sh -s` and asserts that no canary reaches an event, the result, the suggestions or `projects.json`.

### App shell

`src-tauri` is a library (`daminus_app`) plus a two-line `main`. `app::AppCore` holds the `FsStore` (the Tauri `app_config_dir`, `~/Library/Application Support/dev.daminus.app`) and the `ScanService`, and exposes each command as a plain function; `commands.rs` only adapts them to Tauri, so `src-tauri/tests/ipc_e2e.rs` drives the same code with `FakeTransport` and no webview.

- **Commands:** `scan_start(scope?)`, `scan_stop` (answers once the scan has ended, at most 5 s, so the store re-hydrates right after), `scan_status`, `report_latest`, `reveal_config_dir`. Errors are `AppError`. The same list appears in `generate_handler!`, in `build.rs` (which makes Tauri generate one permission per command) and in `src/api/commands.ts`; a Vitest test compares all three with the capability.
- **Events:** one channel, `scan://event`, fed by a pump task that drains the service's receiver. The Vue store `useScanStore` hydrates from `scan_status()` on mount or reload, drops events of ended scans and those already folded in (`seq < next_seq`), and re-hydrates on a gap.
- **Capabilities:** `capabilities/main.json` grants the main window the app's five commands, `core:event` listen/unlisten, `opener:allow-open-url` for `https://*` only and `clipboard-manager:allow-write-text`. No shell, fs or http plugin; Finder is opened by the Rust command `reveal_config_dir`.
- **GUI environment:** an app opened from Finder has launchd's environment. At launch (in parallel with startup) `$SHELL -ilc` prints `env -0` after a marker, with a 3 s limit after which its whole process group is killed; the output is read on a thread with the same deadline (plus 200 ms), since a process that left the group may keep the pipe open; only `PATH`, `SSH_AUTH_SOCK` and `HOME` are kept and set on the `ssh`/`ssh-keygen` processes (`SshTransport::with_env`). The app's own environment is not changed.
- **Tray:** the template mark from `assets/brand/` (idle), the mark at 0.3–0.7 opacity breathing in 16 frames of 150 ms (scanning), the mark with an amber or pink 6 pt dot (warn, crit). Menu: headline counts, scan number, time and the project that needs you, Scan now ⌘R, Open Daminus ⌘O, Quit ⌘Q, worded from `src/i18n/*.json` (`tray.*`). It re-reads the report when a scan ends and after `scan_stop` (the final event can be dropped when the event channel is full); a failed read keeps the last good report, and with none it says "Results could not be read" rather than "No scans yet". Icon changes are serialized with the breathing loop through a counter under the tray lock. Closing the window hides it; the Dock icon reopens it; a second launch focuses the first (`tauri-plugin-single-instance`). Quit (and any exit) calls `ScanService::shutdown()`.
- **Log:** `tauri-plugin-log` writes `~/Library/Logs/dev.daminus.app/daminus.log`, rotated at 1 MB, five files in all. Core `tracing` events reach it through `tracing`'s `log` feature; every line passes `redact_secrets` and is kept on one line.

## Threat model

**Assets to protect**

- Database credentials and other secrets that live in `.env` files, pm2 env and compose files on the servers.
- AI provider API keys stored in the macOS keychain.
- The user's SSH agent and keys: Daminus borrows their access and must never widen it.

**Adversaries and untrusted inputs**

- **A server may be compromised and lie.** Script output is data, never code: lines are parsed as NDJSON with size limits and character filtering, unknown fields are ignored, and nothing from a server is rendered as HTML (`vue/no-v-html` is an error) or executed on the Mac.
- **Config files may be hand-edited wrongly.** `projects.json`, settings and snapshots are parsed leniently where safe and rejected with a typed error where not; a bad file never crashes the app or silently widens what runs remotely.
- **AI output is untrusted.** It is shown as text, never executed. Suggested commands are copy-only.

**Controls**

- **Read-only on servers.** Check scripts only read. They never write, restart, install or call `sudo`. This is enforced by a command allowlist and by running the bundle in a `--read-only` container as a normal user in CI, comparing hashes before and after.
- **Secrets never leave the server.** Scripts read `.env` locally to reach the database and emit only numbers and facts. A canary secret seeded in `.env`, pm2 env and compose must never appear in stdout, stderr, snapshots, events, logs or AI payloads (end-to-end test). Server stderr is not sent back to the Mac.
- **API keys never reach the webview.** Keys stay in the keychain and in Rust; the front end only sees whether a key is set.
- **Webview hardening.** Strict CSP, no remote content, capabilities limited to the app's own commands.
- **Logs are redacted** at the logging layer; secret types do not implement a revealing `Debug`.

| `sec.ports` source | `/proc/net/tcp` + `tcp6`, holder from `/proc/PID/fd` socket links | `ss -ltnp` (absent from minimal images, and `-p` needs root for other users anyway) |
| Security result shape | Findings carry no `value` and an `fp`; "looked, found none" is value 0; at most 50 findings listed with `data.total`; `Unknown` facts may carry `data` | A finding with a size as `value` (size 0 would grade ok) |

| Harness fixtures | Golden `fixtures/ndjson/<distro>/sec_*.ndjson` come from the clean container; findings are kept in `infected/` | One golden from the planted container (every consumer of the fixtures would then replay a compromised host) |

| Ports in discover | `/proc/net/tcp` and `tcp6` LISTEN rows with the bind classified from the address, holder from the socket links of the SSH user's processes (like `sec.ports`), its folder from `find -printf %l` on `cwd`; used to link a `proxy_pass` to the folder of what listens | `ss -ltnp` (absent from minimal images, and it needs root for other users) |
| nginx and sites under aaPanel | `nginx_conf` picks the first readable of `/etc/nginx/nginx.conf`, `/usr/local/nginx/conf/nginx.conf`, `/www/server/nginx/conf/nginx.conf` (else the first that exists, so an unreadable one still gives the `nginx_no_permission` note); `/www/wwwroot` is a `.env` search root and, with `/www`, a shared folder in grouping | Parsing the panel's own data (config text only); searching the whole disk |
| Grouping rules | Linked by registered domain, shared project folder, or a proxy to a published or listening local port; a project needs a domain or at least two parts (code, compose, pm2, `.env`, database container); shared folders (`/var/www`, `/www/wwwroot`, `/srv`, a home) never link; one database engine on a host is used, several are left to the user | Grouping by name similarity; making every compose project or pm2 app a project |

Refines "Host key fingerprint" above, which stays the method for a failed login | A known-hosts parser; `ssh-keyscan` through a proxy (it has none) |
